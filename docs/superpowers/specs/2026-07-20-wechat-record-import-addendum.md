# 微信聊天记录导入补充设计

## 1. 定位

聊天记录导入与实时采集是并列入口：导入用于建立长期历史基线，Accessibility 用于采集近期增量，Root/LSPosed 用于在兼容设备上补充更完整的持续同步。

微信官方迁移或备份文件主要面向恢复流程，系统不能假设它们是可直接读取的开放格式。任何备份包都必须先由导入适配器完成格式识别、完整性检查和解析能力探测；不兼容时只报告原因，不修改原文件，也不把乱码或未知字段写入人物档案。

## 2. 首期输入格式

- 项目定义的标准 JSON 或 JSONL。
- 用户已有工具导出的 CSV、TXT 或 HTML。
- 按时间顺序整理的聊天截图，通过 OCR 后进入人工确认流程。

## 3. 导入流程

1. 用户选择文件或目录，系统只读扫描并计算来源哈希。
2. 识别格式、字符编码、时区、参与者和消息排序规则。
3. 展示抽样预览，由用户确认“我”和对方的身份映射。
4. 解析为统一的 `Message`、`Evidence` 和媒体引用模型。
5. 运行重复检测、时间顺序检查和低置信度检查。
6. 用户确认后以单个事务写入；任一步失败都不产生部分导入。
7. 保存导入批次、来源哈希和解析器版本，保证重复导入具有幂等性。

第一版导入文字、图片路径和图片 OCR 文字。语音、视频、红包、转账、位置等特殊消息仅保留类型、时间和可用的文字摘要，不进行内容理解。原始导入文件默认不复制进项目资料库，只保存来源哈希和用户选择的引用信息。

## 4. 测试与验收

- 覆盖 JSON、JSONL、CSV、TXT、HTML 和聊天截图 OCR。
- 覆盖重复导入、编码异常、时区异常、参与者映射错误和事务回滚。
- 同一来源文件重复导入不得产生重复消息。
- 失败导入不得留下部分消息或人物画像。
- 低置信度内容必须经过人工确认才能进入长期档案。

## 5. 交付顺序调整

1. 基础工程、统一数据模型和本地资料库。
2. 手动输入、标准 JSON/JSONL 导入、云端分析和多回复建议闭环。
3. CSV、TXT、HTML 和聊天截图导入。
4. 微信 Accessibility、截图 OCR 和悬浮入口。
5. 人物持续建档、证据画像和反馈学习。
6. 微信 Root/LSPosed 深度适配和安全降级。
7. Soul、小红书和抖音适配。
